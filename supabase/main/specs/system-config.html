Screen: System Exchange Rates ​

Route ​

/system/exchange-rates

Purpose ​

View official exchange rates auto-populated by a backend bot. Reference data for financial transactions — rates are frozen at transaction time, not read live from this table.

Data Source ​

  • Table(s): SystemExchangeRate
  • RLS Context: Tenant-scoped. RLS filters by tenant's primary/secondary currency pair. No write access.

Fields ​

FieldTypeSourceRequiredEditableNotes
From Currencytextsys_exc_rate_from_currencyN/ANoISO 4217 (typically USD)
To Currencytextsys_exc_rate_to_currencyN/ANoISO 4217
Rate Valuedecimal(19,6)sys_exc_rate_valueN/ANoUp to 6 decimal places
Effective Datedatesys_exc_rate_effective_dateN/ANoSingle day validity
Sourcetextsys_exc_rate_sourceN/ANoe.g., "BCV_OFFICIAL"

Actions / CRUD ​

  • [ ] Create (backend bot only)
  • [x] Read
  • [ ] Update (immutable by design)
  • [ ] Delete (immutable by design)
  • [ ] Special

Related Selectors / Modals ​

  • Currency filter: Filter rates by from-currency or to-currency.
  • Date range picker: Filter by effective date range.

Permissions ​

  • Module code: CFG-001 (inferred)
  • Minimum role permissions: read
  • Special rules: RLS filters rows whose from_currency or to_currency matches Organization.org_currency_primary or org_currency_secondary. If org_use_official_exchange_rate = false, this screen still shows data but the org uses org_custom_exchange_rate instead.

Navigation ​

  • Parent: System Configuration (menu group)
  • Links to: None (view-only reference)

UX Pattern ​

List/Table with date filtering and currency filter

Business Rules / Validations ​

  • Rates are append-only. No user can create, update, or delete rows (backend bot only).
  • A given currency pair MAY have multiple rates on different dates — the effective rate for a transaction is the one with effective_date <= transaction_date ordered by most recent.
  • The org_use_official_exchange_rate flag on the Organization determines whether this table or org_custom_exchange_rate is used for financial calculations.
  • Table MUST be sorted by effective date descending by default.

Notes ​

This is purely a read-only reference. Financial screens (Expense, Payment) freeze the exchange rate at transaction creation time by copying the applicable rate into their own exchange_rate_used field. No live-linking needed.

Screen: Document Types ​

Route ​

/system/document-types

Purpose ​

View valid identity document types for the tenant's country. Used as reference data in employee and client forms.

Data Source ​

  • Table(s): DocumentType
  • RLS Context: FOR SELECT USING (true) — public read, but frontend SHOULD filter by tenant's country.

Fields ​

FieldTypeSourceRequiredEditableNotes
Codetextdoc_type_codeN/ANoAbbreviation, e.g., "V" for Cédula
Nametextdoc_type_nameN/ANoe.g., "Cédula", "Pasaporte"
Countrytextdoc_type_countryN/ANoISO 3166-1 alpha-2

Actions / CRUD ​

  • [ ] Create (system-managed)
  • [x] Read
  • [ ] Update (system-managed)
  • [ ] Delete (system-managed)
  • [ ] Special

Related Selectors / Modals ​

  • None (consumed as dropdown by Employee and Client forms)

Permissions ​

  • Module code: CFG-001 (inferred, grouped with System Config)
  • Minimum role permissions: read
  • Special rules: Frontend MUST filter rows by doc_type_country = org_country. This is an application-level filter since the RLS policy allows all reads.

Navigation ​

  • Parent: System Configuration (menu group)
  • Links to: None (reference data consumed by other screens)

UX Pattern ​

Reference table (read-only list)

Business Rules / Validations ​

  • No user CRUD — this is system-seeded data maintained via DB migration or seed script.
  • Frontend MUST filter by the tenant's country (from Organization.org_country) when using as dropdown.
  • The dropdown shows: "Code — Name" format, e.g., "V — Cédula"

Notes ​

This is the simplest screen in the system. Only needed as a standalone screen for admin reference. In practice, most users will only interact with Document Types through selectors on Employee/Client forms, not this standalone page.

Screen: System Payment Methods ​

Route ​

/system/payment-methods

Purpose ​

View available payment gateway types supported by the Bookia platform. Reference data for the Organization Payment Methods configuration screen.

Data Source ​

  • Table(s): SystemPaymentMethod, SystemPaymentMethodCountry
  • RLS Context: FOR SELECT USING (true) — public read. Frontend MUST filter by tenant's country and active status.

Fields ​

FieldTypeSourceRequiredEditableNotes
Method Codetextsys_pay_meth_codeN/ANoe.g., "pago_movil", "zelle"
Nametextsys_pay_meth_nameN/ANoDisplay name
Statusbadgesys_pay_meth_status_codeN/ANo1=Active, 0=Blocked
Countriestext[]SystemPaymentMethodCountry (joined)N/ANoComma-separated list of ISO country codes

Actions / CRUD ​

  • [ ] Create (system-managed)
  • [x] Read
  • [ ] Update (system-managed)
  • [ ] Delete (system-managed)
  • [ ] Special

Related Selectors / Modals ​

  • Country filter: Filter by tenant's country (default) or select a different country to preview.

Permissions ​

  • Module code: CFG-001 (inferred, grouped with System Config)
  • Minimum role permissions: read
  • Special rules: RLS allows all reads; frontend filters by sys_pay_meth_status_code = 1 AND existence in SystemPaymentMethodCountry for the tenant's country.

Navigation ​

  • Parent: System Configuration (menu group)
  • Links to: Organization Payment Methods (parent config screen uses this as source)

UX Pattern ​

Reference list with country filter and status badges

Business Rules / Validations ​

  • ONLY methods with sys_pay_meth_status_code = 1 SHALL be shown in the default view.
  • Methods MUST have an entry in SystemPaymentMethodCountry for the tenant's country to be shown as "available".
  • The Organization Payment Methods screen uses this table as its source for selecting which method to affiliate.
  • Methods with status = 0 (blocked) SHOULD be hidden from dropdowns in other screens but MAY appear here for admin reference.

Notes ​

This data is typically stable — seeded at platform launch and rarely changed. The SystemPaymentMethodCountry join provides geographic segmentation (e.g., Zelle is US-only, Pago Móvil is Venezuela-only).

Screen: Plan Management ​

Route ​

/admin/plans

Purpose ​

Create, edit, deactivate, and delete subscription plans. Super-admin only screen for managing the SaaS monetization catalog.

Data Source ​

  • Table(s): Plan
  • RLS Context: No RLS — restricted by admin API key or super-admin access only.

Fields ​

FieldTypeSourceRequiredEditableNotes
Nametextpln_nameYesYesCommercial name, e.g., "Plan Pro"
Descriptiontextpln_descriptionNoYesMarketing text, nullable
Max Employeesnumberpln_max_employeesNoYesNULL = unlimited
Max Clientsnumberpln_max_clientsNoYesNULL = unlimited
Max Resourcesnumberpln_max_resourcesNoYesCHECK >= 0
Max Servicesnumberpln_max_servicesNoYesCHECK >= 0
Currencyselectpln_currency_codeYesYesISO 4217
Monthly Pricedecimal(10,2)pln_monthly_priceYesYes>= 0
Annual Pricedecimal(10,2)pln_annual_priceYesYes>= 0
Statusselectpln_status_codeYesYes1=Active, 0=Archived

Actions / CRUD ​

  • [x] Create
  • [x] Read
  • [x] Update
  • [x] Delete (soft: set status to 0)
  • [ ] Special

Related Selectors / Modals ​

  • Menu module selector: (embedded or separate Plan-Menu Assignment screen) links PlanMenu entries to this plan.

Permissions ​

  • Module code: SYS-001 (inferred — super admin)
  • Minimum role permissions: write (full CRUD)
  • Special rules: ONLY accessible to super admin accounts. API-key gated or admin-only auth. No RLS policies — the Supabase client used MUST have service_role or a custom admin JWT claim.

Navigation ​

  • Parent: System / Admin (menu group)
  • Links to: Plan-Menu Assignment (child screen)

UX Pattern ​

List + Form (modal or page)

Business Rules / Validations ​

  • pln_annual_price SHOULD be less than pln_monthly_price * 12 (annual discount).
  • pln_max_resources MUST be >= 0 or NULL; DB trigger enforces CHECK constraint.
  • pln_max_services MUST be >= 0 or NULL; DB trigger enforces CHECK constraint.
  • Setting status to 0 (archived) MUST NOT affect existing OrganizationPlan subscriptions — only prevents new subscriptions.
  • Deleting a plan with active OrganizationPlan rows MUST be blocked (foreign key or application check).
  • Plan limits are enforced via DB triggers at INSERT time on Employee, Service, Resource, and ClientOrganization tables.
  • At least ONE plan MUST exist and be active for the system to be usable in onboarding.

Notes ​

This is a back-office screen, not part of the tenant-facing app. Consider building it as a separate admin panel or a protected route with a super-admin flag. The plan's pln_currency_code affects how prices display but not the operational currency of tenants (each org has its own currency).

Screen: Plan-Menu Assignment ​

Route ​

/admin/plans/:planId/menus

Purpose ​

Toggle which SystemMenu modules a subscription plan unlocks. This is the feature flag engine — if a module is not in PlanMenu, no tenant on that plan can access it at the DB level.

Data Source ​

  • Table(s): PlanMenu, SystemMenu
  • RLS Context: No RLS — same super-admin access as Plan Management.

Fields ​

FieldTypeSourceRequiredEditableNotes
Plan Nametext (read-only)Plan.pln_nameN/ANoHeader showing current plan
Module NametextSystemMenu.sys_menu_nameN/ANoDisplayed as tree node
Module PathtextSystemMenu.sys_menu_pathN/ANoRouter path, helps identify module
Module Transaction CodetextSystemMenu.sys_menu_transaction_codeN/ANoe.g., "FIN-001"
EnabledcheckboxPlanMenu (if row exists)N/ANoChecked = plan has access to this module

Actions / CRUD ​

  • [x] Create (link plan to menu module)
  • [x] Read (list all modules with enabled status)
  • [x] Update (toggle enabled/disabled)
  • [x] Delete (remove plan-module link)
  • [ ] Special

Related Selectors / Modals ​

  • SystemMenu tree selector: Renders the full SystemMenu hierarchy as a collapsible tree. Parent nodes can be toggled (auto-toggles all children). Transaction codes shown as badges.

Permissions ​

  • Module code: SYS-001 (inferred — super admin)
  • Minimum role permissions: write (full CRUD)
  • Special rules: Same super-admin gating as Plan Management. Changes take effect immediately — existing tenants on this plan will gain/lose access on their next query.

Navigation ​

  • Parent: Plan Management (linked from plan list row or detail page)
  • Links to: None

UX Pattern ​

Tree checkbox matrix (Plan × Module)

Business Rules / Validations ​

  • Deleting a PlanMenu row immediately revokes access to that module for ALL tenants on this plan (DB-enforced via RLS policy that checks PlanMenu).
  • Adding a PlanMenu row immediately grants access.
  • If a parent SystemMenu node is not enabled, children SHOULD be visually disabled (uncheckable) or the parent must be enabled first.
  • The default Admin role onboarding grants ALL active modules — PlanMenu is the gating layer BEFORE OrganizationRoleMenu.
  • Changes MUST be confirmed with a warning: "This will affect ALL tenants on this plan."

Notes ​

This is the most critical gating screen. Every OrganizationRoleMenu check at the DB level starts by confirming the module exists in PlanMenu for the tenant's plan. Consider adding a "review impact" button that shows how many active tenants would be affected by a change. The tree should mirror the SystemMenu hierarchy exactly (parent → child → grandchild structure with sys_menu_level and sys_menu_parent_id).

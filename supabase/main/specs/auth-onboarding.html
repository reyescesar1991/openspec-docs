Auth & Onboarding Specification ​

Screen: Login ​

Route ​

/login

Purpose ​

Authenticate user via email magic link, password, or OAuth provider.

Data Source ​

  • Table(s): Supabase Auth → auth.users → triggers handle_new_user() → User, UserPreference
  • RLS Context: Pre-tenant (public). No tenant context required.

Fields ​

FieldTypeSourceRequiredEditableNotes
EmailtextUser inputYesYesRFC 5322 validated
PasswordpasswordUser inputConditionalYesRequired only if email auth mode; min 8 chars
OAuth Buttonsbutton groupProvider configNoN/AGoogle, etc. — configurable per deployment

Actions / CRUD ​

  • [ ] Create
  • [ ] Read
  • [ ] Update
  • [ ] Delete
  • [x] Special: Authenticate via Supabase Auth (signInWithOtp, signInWithPassword, signInWithOAuth)

Related Selectors / Modals ​

  • None

Permissions ​

  • Module code: AUTH
  • Minimum role permissions: None (public)
  • Special rules: Redirect to Tenant Switcher if user belongs to >1 org; redirect to Dashboard if single org.

Navigation ​

  • Parent: None (standalone landing)
  • Links to: Tenant Switcher or Dashboard (post-login)

UX Pattern ​

Form / Landing page

Business Rules / Validations ​

  • Email format MUST be RFC 5322 compliant
  • Password MUST be >= 8 characters when using email auth
  • After successful login, MUST redirect: >1 org → Tenant Switcher, exactly 1 org → Dashboard, 0 orgs → Onboarding Wizard

Notes ​

Supabase Auth handles all token management. Frontend only triggers the auth method and handles session callbacks via onAuthStateChange. The login screen is the ONLY public page accessible pre-auth; all other routes redirect here.

Screen: Sign Up ​

Route ​

/signup

Purpose ​

Create a new user identity (no organization yet). Entry point for new SaaS users.

Data Source ​

  • Table(s): Supabase Auth → auth.users → trigger handle_new_user() creates User + UserPreference
  • RLS Context: Pre-tenant (public). No tenant context.

Fields ​

FieldTypeSourceRequiredEditableNotes
NametextUser inputYesYesFull name; stored in User via trigger or post-signup
EmailtextUser inputYesYesMust be unique in auth.users
PasswordpasswordUser inputYesYesMin 8 chars; Supabase Auth hashing
Auth ProviderselectConfigNoN/AOAuth provider buttons displayed instead of form when applicable

Actions / CRUD ​

  • [x] Create (auth identity)
  • [ ] Read
  • [ ] Update
  • [ ] Delete
  • [x] Special: Supabase Auth sign-up (signUp)

Related Selectors / Modals ​

  • None

Permissions ​

  • Module code: AUTH
  • Minimum role permissions: None (public)
  • Special rules: After signup, MUST redirect to Onboarding Wizard (first org creation)

Navigation ​

  • Parent: Login (link from login page)
  • Links to: Organization Onboarding Wizard (post-signup)

UX Pattern ​

Form

Business Rules / Validations ​

  • Email MUST NOT already exist in auth.users (Supabase enforces this)
  • Password MUST be >= 8 characters
  • usr_auth_provider in User table is set to the provider used (email, google, etc.)
  • UserPreference auto-created via DB trigger with defaults (language: es, theme: light, color: blue)

Notes ​

After Supabase Auth signs up the user, the handle_new_user() DB trigger creates the User and UserPreference rows. The frontend then navigates to the Onboarding Wizard. If the user cancels onboarding, they can access it later from a prompt in the app shell.

Screen: Organization Onboarding Wizard ​

Route ​

/onboarding

Purpose ​

First-time tenant bootstrap: create organization, assign plan, create admin role, and link the creating user as the first admin employee.

Data Source ​

  • Table(s): Organization, OrganizationPlan, OrganizationRole, OrganizationRoleMenu, EmployeeOrganization, Employee, Plan
  • RLS Context: Authenticated but pre-tenant. This screen CREATES the tenant — no app.current_tenant_id yet.

Actions / CRUD ​

  • [x] Create (Organization, OrganizationPlan, OrganizationRole, EmployeeOrganization, Employee, OrganizationRoleMenu)
  • [ ] Read (Plan list for selection)
  • [ ] Update
  • [ ] Delete
  • [ ] Special: Transactional bootstrap — ALL creates MUST succeed or rollback as a unit

Related Selectors / Modals ​

  • Plan selector card: Shows Plan cards with name, description, limits, and pricing. Highlights selected.
  • Country picker: ISO 3166-1 alpha-2 list.
  • Timezone picker: IANA TZ list filtered by selected country.
  • Currency picker: ISO 4217 list.
  • DocumentType dropdown: Filtered by selected country.

Permissions ​

  • Module code: AUTH
  • Minimum role permissions: Authenticated (any signed-up user)
  • Special rules: This is a one-time flow per user (until first org is created). User cannot have 0 orgs after initial creation unless all are deleted.

Navigation ​

  • Parent: Sign Up (post-signup redirect)
  • Links to: Tenant Switcher (post-completion)

UX Pattern ​

Wizard (multi-step form with progress indicator, 4 steps, Back/Next/Submit navigation)

Business Rules / Validations ​

  • Org name MUST be unique across the platform (enforced by application or unique constraint)
  • Country MUST be ISO 3166-1 alpha-2; timezone MUST be valid IANA
  • Plan selection is REQUIRED — no plan means no service
  • On submission, in a single DB transaction or edge function:
    1. INSERT Organization
    2. INSERT OrganizationPlan
    3. Find or create Employee for the current user
    4. INSERT OrganizationRole with name "Admin", org_role_is_default = true
    5. INSERT EmployeeOrganization linking employee + org + admin role
    6. INSERT OrganizationRoleMenu for ALL active SystemMenu entries (Admin gets full CRUD on everything by default)
  • After completion, set app.current_tenant_id to the new org and redirect to Tenant Switcher

Notes ​

This is the most critical bootstrap flow in the system. Consider using a Supabase Edge Function to execute the transactional steps atomically. The wizard MUST handle the case where the user's Employee record already exists (global identity) — use find_or_create_employee() flow. If the user refreshes mid-wizard, preserve step state in URL params or session storage.

Screen: Tenant Switcher ​

Route ​

/switch-tenant (embedded in app shell layout, accessible from header)

Purpose ​

Allow the authenticated user to switch between organizations they belong to. Sets app.current_tenant_id and app.current_user_role_id for all subsequent queries.

Data Source ​

  • Table(s): EmployeeOrganization (via Employee → User), Organization
  • RLS Context: Authenticated. Query filters: employee -> user_id = auth.uid() AND emp_org_status_code = 1.

Fields ​

FieldTypeSourceRequiredEditableNotes
Organization Nametext (display)Organization.org_nameN/AN/ADisplayed in dropdown
Current IndicatorbadgeBooleanN/AN/AHighlight currently active org
Role Nametext (display)OrganizationRole.org_role_nameN/AN/ADisplayed as subtitle

Actions / CRUD ​

  • [ ] Create
  • [x] Read (list accessible orgs)
  • [ ] Update
  • [ ] Delete
  • [x] Special: Switch tenant — sets app.current_tenant_id and app.current_user_role_id in local state/middleware

Related Selectors / Modals ​

  • None (simple dropdown or sidebar switch)

Permissions ​

  • Module code: AUTH
  • Minimum role permissions: Authenticated + active EmployeeOrganization (status_code = 1)
  • Special rules: If user has exactly 1 org, auto-select on login (skip dropdown)

Navigation ​

  • Parent: App Shell (header/sidebar)
  • Links to: All tenant-scoped screens (indirectly — switching changes data context)

UX Pattern ​

Dropdown / Sidebar selector

Business Rules / Validations ​

  • MUST show ALL orgs where EmployeeOrganization.emp_org_status_code = 1 for the current user
  • On org selection:
    1. Set app.current_tenant_id to selected Organization.id
    2. Set app.current_user_role_id to the user's OrganizationRole.id for that org
    3. Re-fetch navigation tree (SystemMenu × PlanMenu × OrganizationRoleMenu)
    4. Redirect to Dashboard (or stay on current page if accessible in new org context)
  • If current tenant becomes inactive or user's role is revoked, MUST auto-switch to next available org or show empty state

Notes ​

This screen is the architectural keystone of the multi-tenant system. The app.current_tenant_id and app.current_user_role_id MUST be injected into every Supabase API call (as session variables or headers). Implementation: store in React context, pass as Supabase session variables via supabase.rpc() or custom headers. Must be prominent in the app header — never hidden in sub-menus.
